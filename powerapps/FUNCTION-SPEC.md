### F-03 파트너사별 실적 · 기존 예약을 파트너로 바꾸기 🔴

**A. 파트너사별 실적 (통계 화면 하위 표)**

- 대상: `Category = 고객 방문` 이고 `ClientType = 파트너사 소개 고객` 인 건 (조회 기간 · 센터 범위 필터는 다른 통계와 동일).
- **파트너사 묶기 키**: 이름을 소문자로 바꾸고 공백 · `(주)` · `㈜` · `주식회사` 를 제거한 값. 키가 같으면 같은 파트너사 (`LG 전자` = `lg전자` = `(주)LG전자`).
- 이름이 비어 있으면 `(파트너사명 미입력)` 으로 묶음.
- 표시 이름: 그 파트너사의 **가장 최근 방문**에 적힌 표기.
- 열: 순위 · 파트너사 · **소개 방문 건수** · **방문 인원**(`Heads` 합계) · **소개 고객사 수**(같은 업체는 1곳, 업체명도 같은 규칙으로 정규화) · 최근 방문일.
- 정렬: 건수 ↓, 방문 인원 ↓, 이름(가나다). 상위 10곳 + `전체 n곳 보기` 토글. 줄을 누르면 그 파트너사가 소개한 방문 목록.
- 방문 유형 열에 `고객·파트너사` 추가 (F-02-7 과 연결).
- 통계 엑셀 내보내기에는 시트 `파트너사별(기간)` 추가 — Power Apps 는 엑셀 내보내기를 제외했으므로 **화면 표시만**.

**B. 기존 예약을 파트너로 바꾸기 (관리자)**

- 관리자 요청 상세에서 `고객 유형` 을 **빠른 편집**(전체 수정 창을 열지 않고)으로 바꿀 수 있음: 기존 / 신규 / 파트너사 + 파트너사명.
- 파트너사명 입력칸에는 **이미 기록된 파트너사 이름을 많이 소개한 순으로 제안** (같은 곳이 다르게 적히는 것을 막는 용도).
- 수정은 목록 상태(승인 · 완료 등)를 바꾸지 않음. 후기 메일 발송 기록 등 다른 열은 보존.

- 한 줄에 한 명, 인솔자는 `이름 직책 (인솔자)`, 운영 인원은 `이름 직책`. 순서: 인솔자(명단순) → 운영 인원(명단순) → 명단에 없는 기존 기록 줄(그대로 보존).
- 읽을 때: `(인솔자)` · `[인솔자]` · `인솔: ` · 예전 `(메인)` 표시 모두 인솔자로 인식. **표시 없이 적힌 예전 기록은 운영 가능자는 운영 인원, 불가자(팀장)는 인솔자**로 해석.
- 명단 밖 이름은 `others` 로 보존 (지우지 않음).

**5. 화면 3종**

| 화면 | 내용 |
| --- | --- |
| 배정 (달력 + 패널) | 월 달력에서 배정 대상 방문을 고르면 오른쪽에 `배정` 패널: 인솔자 선택(여러 명) · 운영 인원 체크(**전체 선택 토글**) · 저장. 미배정 방문은 눈에 띄게(빨간 점선). 모바일에서도 달력 · 탭 바가 동작(상단 메뉴 가로 스크롤) |

**6. 시간 · M/M 계산**
- 투어 1건 = **1타임 = 반일 4시간** (실제 투어 길이와 무관, 복합 투어도 Lab 구간 한 타임). `SESSION_HOURS = 4`.
- 하루 근무 `HOURS_PER_DAY = 8`. 그 달 **근무일 = 주말 · 공휴일 제외 일수**(공휴일은 `HolidayKeys`).
- **M/M = 투입 시간 ÷ (근무일 × 8)**. 소수 둘째 자리 반올림(`0.075 → 0.08`, 부동소수 보정 +1e-9).
- 사람별 집계 열: 인솔 건수 · 운영 건수 · 투입 시간 · M/M. 주간은 분모를 **그 주의 근무 시간**으로.
- Lab 시간대 판정(`labSlot`): 복합 투어는 `lab`/`combined` 구간 슬롯, Lab 투어 · 수기는 방문 시간, 시간 없으면 `시간 미정`.

**7. Power Apps 구현 메모**
- 승인 · 완료 건만 읽어 컬렉션에 두고 `Guides` 텍스트를 파싱하는 수식이 필요 (`Split` · `ForAll`). 규칙 4 의 파싱이 복잡하면 **`GuideAssign` 목록(RequestNo · Member · Role)으로 정규화**하는 편이 수식이 단순해짐 — 이 경우 웹 `Guides` 텍스트는 마이그레이션 때 1회 변환.
- 저장은 승인 · 거절과 같은 방식(`Patch`) + 연속 클릭 잠금 `locWorking`.

### F-06 방문 완료 시 후기(방명록) 요청 메일 🔴

웹 `Code.gs` `sendFeedbackMail_` · `feedbackMailHtml_`, `src/admin/feedbackMail.ts`. **관리자가 상태를 `완료` 로 바꾸는 순간** 방문자에게 1회 발송.

**발송 조건 (모두 만족해야 함 / 아니면 사유 표시)**

| 사유 | 조건 | 관리자에게 보이는 문구 |
| --- | --- | --- |
| `already` | 이미 보냄 (`FeedbackMailAt` 값 있음) | 이미 만족도 요청 메일을 보낸 예약입니다. |
| `noConsent` | 수기 등록이거나 개인정보 동의 기록 없음 | 수기 등록 예약이라(개인정보 동의 기록 없음) … 보내지 않았습니다. |
| `before` | **2026-10-22 이전에 신청**한 예약 (동의문에 이 용도를 넣은 날. 서버 속성 `FEEDBACK_MAIL_FROM` 으로 변경) | 개인정보 동의 문구에 이 용도를 넣기 전에 신청한 예약이라 … 보내지 않았습니다. |
| `future` | 방문일이 아직 지나지 않음 | 방문일이 아직 지나지 않아 … |
| `noRecipients` | 올바른 이메일 방문자 없음 | 방문자 이메일이 없어 … |
| `quota` | 일일 메일 발송 한도 부족 | 오늘 메일 발송 한도가 부족해 … |
| `error` | 발송 중 오류 | 오류가 났습니다. **완료 처리는 되었습니다.** |

- 수신자: 방문자 명단 중 **이메일 형식이 맞는 사람**, 같은 주소는 1번 (대소문자 무시). 한 사람씩 따로 발송, 일부 실패해도 나머지는 발송(`발송 n명 / 실패 m명` 표시).
- **한 명이라도 보내면 `FeedbackMailAt`(발송 시각)을 기록**해 같은 예약에는 다시 보내지 않음. 관리자 수정이 이 값을 지우면 안 됨.
- **실패해도 완료 처리는 그대로** 유지.
- 메일 내용 (한국어 / 외국어 투어는 **영문을 위에, 한국어를 아래**):
  - 제목: `[브랜드] 방문해 주셔서 감사합니다 · 만족도와 개선 의견을 남겨 주세요` / 외국어 투어 `[브랜드] Thank you for visiting · 방문해 주셔서 감사합니다`
  - 본문: `{이름} 님, {방문일} 투어에 방문해 주셔서 감사합니다. **이번 방문**은 어떠셨나요? …`, 일정 박스, 남겨 달라는 항목 3가지(**만족도(별점) · 좋았던 점 · 개선했으면 하는 점**), 버튼 `방명록에 후기 남기기`(→ 방명록 주소), 안내 `1분이면 충분합니다 … 이름과 소속은 일부만 공개`, **발신 전용 안내**(회신 불가, 문의는 담당 센터 담당자에게).
  - 발신 전용: 회신 주소를 두지 않음 (`noReply`). 날짜는 풀 표기(`2026년 10월 22일`, 영문 `October 22, 2026`).
- 관리자 요청 상세에 `만족도 메일` 행: `방문자에게 발송됨 · {날짜}` / `보내지 않음`.
- **개인정보 동의문 (신청 화면 · Forms 모두)** 목적 항목에 반드시 포함: `방문 종료 후 만족도 · 개선 의견 조사 안내 메일 발송(방문자 이메일로 1회)`.

**Power Apps 쪽 차이 · 확인 필요**

1. 이메일 출처가 다름: 웹은 신청자가 입력한 방문자 명단, Power Apps 는 **참석자 Forms 의 `Email`**(`VisitAttendees.Email`). 참석자 본인이 동의한 Forms 이므로 **Forms 동의 문구에 위 목적을 넣어야 함** (`2-forms/attendee-form.md` 수정).
2. 흐름 C 에 사례 `완료` 추가(또는 별도 흐름): 조건 검사 → `VisitAttendees` 에서 이메일 수집 → 중복 제거 → 각자 발송 → `VisitRequests.FeedbackMailAt` 기록. **Outlook 일일 발송 한도**(웹의 Gmail 한도와 다름)를 IT 와 확인.
3. **보관 기간 충돌**: 참석자 정보는 방문일 1년 후 삭제(흐름 D). 후기 메일은 방문 직후 1회라 문제 없음.
4. 메일 링크가 가리키는 **방명록**(F-10) 을 Power Apps 로 옮길지 결정이 먼저 필요 (6장).
5. 관리자 화면 `방문 완료` 도 승인 · 거절처럼 **미리보기 창**(10/19 PA 개선)에서 처리하는 것이 일관적 — 완료 시 `후기 메일 n명에게 발송됨` 또는 위 사유 문구 표시.
